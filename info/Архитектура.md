# Архитектура Ingredify

## Назначение документа

Документ описывает архитектуру MVP Ingredify: веб-приложения для регистрации пользователя, входа в аккаунт и ведения приватной базы рецептов.

MVP не включает публичные рецепты, доступы по ссылке, группы, подписки, поиск, загрузку изображений и мобильное приложение. Эти возможности учитываются как будущие расширения, но не усложняют первую реализацию.

## Границы MVP

В MVP входят:

- регистрация по email и паролю
- вход по email и паролю
- сессии на 30 дней
- хранение сессий в Redis
- профиль пользователя в режиме просмотра
- список рецептов пользователя
- просмотр рецепта
- создание рецепта
- редактирование рецепта
- физическое удаление рецепта
- структурированные ингредиенты
- структурированные шаги приготовления
- справочник единиц измерения
- изображение рецепта как URL

В MVP не входят:

- мобильное приложение
- внешний публичный API
- публичные рецепты
- рецепты по ссылке
- группы доступа
- платные доступы
- мультиязычный интерфейс
- изменение профиля
- сброс пароля
- подтверждение email
- загрузка изображений
- черновики рецептов
- поиск и фильтрация
- категории, теги и полки
- rate limit для входа и регистрации
- GitHub Actions

## Технологический стек

### Приложение

- Next.js
- App Router
- TypeScript
- Server Actions
- React forms через Server Actions и `useActionState`
- Zod для серверной валидации форм
- shadcn/ui
- Tailwind

### Данные

- PostgreSQL как основная БД
- Prisma ORM
- Prisma schema в `prisma/schema.prisma`
- Prisma Client генерируется в `./prisma/client`
- alias для Prisma Client: `@prisma/`
- Redis для хранения сессий

### Инфраструктура

- Docker
- Docker Compose в корне проекта
- PostgreSQL и Redis запускаются локально через Docker Compose
- `.env.example` обязателен
- production на этапе MVP не проектируется
- будущий production предполагается self-hosted

### Тестирование

- Jest для unit и integration тестов
- Testing Library для тестирования компонентов
- Playwright для e2e сценариев
- ESLint и Prettier стандартно

## Структура проекта

Используется `src/` и Feature-Sliced Design с адаптацией под Next.js App Router.

```text
src/
  app/
  views/
  widgets/
  features/
  entities/
  shared/
prisma/
  schema.prisma
  client/
docker-compose.yml
.env.example
```

### `src/app/`

Маршруты Next.js App Router.

Здесь находятся:

- layouts
- route segments
- metadata
- server pages
- подключение view-слоя

`src/app/` не должен становиться местом для основной бизнес-логики.

### `src/views/`

Композиция страниц. Этот слой используется вместо классического FSD `pages`, потому что в Next.js App Router папка `app/` уже занята маршрутизацией.

Примеры:

- `src/views/auth/login`
- `src/views/auth/register`
- `src/views/profile`
- `src/views/recipes/list`
- `src/views/recipes/details`
- `src/views/recipes/create`
- `src/views/recipes/edit`

### `src/widgets/`

Крупные блоки интерфейса, которые собирают несколько features/entities.

Примеры:

- верхняя навигация
- список рецептов
- карточка профиля
- форма рецепта как крупный экранный блок
- внутренние UI-части widget, не переиспользуемые снаружи (например, блок КБЖУ в `recipe-intro`)

### `src/features/`

Пользовательские действия и сценарии.

Примеры:

- регистрация
- вход
- выход
- создание рецепта
- редактирование рецепта
- удаление рецепта
- sidebar ингредиентов с масштабированием выхода

Server Actions для мутаций размещаются на уровне соответствующей feature.

Внутренний UI feature (не экспортируемый из `index.ts`) размещается в `ui/` внутри соответствующей feature.

### `src/entities/`

Доменные сущности приложения.

Примеры:

- user
- session
- recipe
- ingredient

Здесь размещаются типы, схемы, серверные запросы чтения, мапперы и переиспользуемые UI-фрагменты, привязанные к доменной модели.

Сегменты слайса:

- `model/` — типы и константы сущности
- `api/` — серверные запросы чтения (`getRecipe`, `getCurrentUser`)
- `lib/` — чистые функции над моделью
- `ui/` — переиспользуемые UI-примитивы сущности (например, `IngredientSticker`)

#### Критерии размещения UI

| Слой | Когда использовать | Пример |
|------|-------------------|--------|
| `entities/` | Есть бизнес-понятие + `model/` и/или `api/`; либо переиспользуемый UI-примитив с типом | `recipe`, `user`, `IngredientSticker` |
| `features/` | Пользовательский сценарий с логикой и своим UI | `ingredient-sidebar` |
| `views/` | Блок конкретной страницы, не переиспользуется | `equipment-card`, `comments-card`, `cooking-step` |
| `widgets/` | Часть крупного составного блока | `nutrition-stats` внутри `recipe-intro` |

Read API (`getRecipe`, `getCurrentUser`) остаётся в `entities/*/api/`. Отдельный слой `core` не используется.

### `src/shared/`

Общий код, не привязанный к конкретной бизнес-сущности.

Примеры:

- UI-примитивы
- helpers
- конфиги
- Prisma client wrapper
- Redis client
- auth/session utilities
- env validation

## Маршруты MVP

Предварительная структура маршрутов:

```text
/
/register
/login
/profile
/recipes
/recipes/new
/recipes/[recipeId]
/recipes/[recipeId]/edit
```

Все маршруты, кроме `/register` и `/login`, требуют активной сессии.

## Модель данных

### User

Пользователь системы.

Минимальные поля:

- `id`
- `email`
- `passwordHash`
- `name`
- `createdAt`
- `updatedAt`

Ограничения:

- `email` уникален
- удаление пользователя физическое

### Session

Сессии хранятся в Redis, а не в PostgreSQL.

Рекомендуемая модель значения в Redis:

- `sessionId`
- `userId`
- `createdAt`
- `expiresAt`

Ключ:

```text
session:{sessionId}
```

TTL:

```text
30 дней
```

Пользователь может иметь несколько активных сессий на разных устройствах.

### Recipe

Приватный рецепт пользователя.

Минимальные поля:

- `id`
- `ownerId`
- `title`
- `description`
- `imageUrl`
- `createdAt`
- `updatedAt`

Ограничения:

- рецепт принадлежит одному пользователю
- в MVP все рецепты приватные
- поля видимости для будущих публичных/групповых доступов не добавляются в MVP
- удаление физическое

### RecipeIngredient

Структурированный ингредиент рецепта.

Минимальные поля:

- `id`
- `recipeId`
- `name`
- `quantity`
- `unitId`
- `position`
- `createdAt`
- `updatedAt`

Решения:

- название ингредиента в MVP свободным текстом
- количество числовое
- значения вроде "по вкусу" в MVP не поддерживаются
- единица измерения берется из справочника

### MeasurementUnit

Справочник единиц измерения.

Стартовый набор:

- `г`
- `кг`
- `мл`
- `л`
- `шт`
- `ч. л.`
- `ст. л.`
- `щепотка`

Минимальные поля:

- `id`
- `name`
- `shortName`
- `createdAt`
- `updatedAt`

### RecipeStep

Шаг приготовления.

Минимальные поля:

- `id`
- `recipeId`
- `text`
- `position`
- `createdAt`
- `updatedAt`

В MVP шаг содержит только текст.

### SecurityEvent

События безопасности хранятся в PostgreSQL.

Минимальные события:

- успешный вход
- неуспешный вход
- выход

Минимальные поля:

- `id`
- `userId`
- `type`
- `email`
- `ip`
- `userAgent`
- `createdAt`

`userId` может быть пустым для неуспешной попытки входа, если пользователь не найден.

## Индексы

В MVP не закладываются индексы под будущий полнотекстовый поиск.

Минимальные индексы:

- уникальный индекс `User.email`
- индекс `Recipe.ownerId`
- составной индекс `Recipe.ownerId + Recipe.createdAt` для списка рецептов пользователя
- индекс `RecipeIngredient.recipeId`
- индекс `RecipeStep.recipeId`
- индекс `SecurityEvent.userId`
- индекс `SecurityEvent.createdAt`

## Авторизация и сессии

### Регистрация

Пользователь регистрируется по email, имени и паролю.

Пароль:

- минимум 6 символов
- без сложных правил на MVP
- хранится только в виде хеша

После регистрации можно автоматически создать сессию или отправить пользователя на вход. Для простоты MVP предпочтительно автоматически авторизовать пользователя после регистрации.

### Вход

Пользователь входит по email и паролю.

После успешной проверки:

- создается `sessionId`
- сессия записывается в Redis
- браузеру устанавливается cookie сессии
- создается событие безопасности

### Cookie сессии

Cookie:

- `httpOnly`
- `sameSite: "lax"`
- `secure: true` в production
- срок жизни 30 дней

Чекбокс "запомнить меня" в MVP не делается.

### Выход

При выходе:

- текущая сессия удаляется из Redis
- cookie очищается
- создается событие безопасности

### Проверка доступа

Каждое действие с рецептом проверяет:

- пользователь авторизован
- рецепт принадлежит текущему пользователю

Нельзя полагаться только на скрытие кнопок в интерфейсе. Проверка прав обязательна на сервере.

## Server Actions

Мутации реализуются через Server Actions.

Основные actions:

- `register`
- `login`
- `logout`
- `createRecipe`
- `updateRecipe`
- `deleteRecipe`

Каждая action должна:

- валидировать входные данные через Zod
- получать текущего пользователя на сервере
- проверять права доступа
- возвращать типизированный результат для формы
- не раскрывать внутренние ошибки пользователю

## Валидация

Основной источник истины — серверная Zod-валидация.

Клиентская валидация допустима для удобства пользователя, но не заменяет серверную.

Минимальные правила:

- email должен быть валидным
- пароль минимум 6 символов
- имя пользователя обязательно
- название рецепта обязательно
- описание рецепта обязательно
- `imageUrl` должен быть URL или пустым
- рецепт должен иметь хотя бы один ингредиент
- ингредиент должен иметь название, количество и единицу измерения
- количество ингредиента должно быть числом больше нуля
- рецепт должен иметь хотя бы один шаг
- текст шага обязателен

## Безопасность

Для MVP:

- session cookie `httpOnly`
- `sameSite: "lax"`
- `secure` в production
- права проверяются на сервере
- пароли хешируются
- security events пишутся в PostgreSQL
- отдельный CSRF-token не вводится
- rate limit на login/register не вводится

CSRF-защита может быть пересмотрена, если появятся cookie-based API routes для внешних клиентов.

Rate limit стоит добавить после MVP перед публичным запуском.

- валидационные схемы
- helpers для сессий
- мапперы данных

### Integration

Покрыть:

- регистрацию
- вход
- выход
- создание сессии в Redis
- создание рецепта
- редактирование рецепта

### E2E

Ключевые сценарии Playwright:

- пользователь регистрируется и попадает в аккаунт
- пользователь входит и выходит
- пользователь создает рецепт
- пользователь редактирует рецепт
- пользователь удаляет рецепт
- неавторизованный пользователь не видит приватные страницы
