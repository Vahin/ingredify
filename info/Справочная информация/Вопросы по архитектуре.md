### 31. Нужно ли сразу проектировать индексы под будущий поиск, или пока только минимальные индексы для `ownerId`/`email`?

Ответ: Не закладываем заранее

Пояснение от агента:

Индексы в БД ускоряют частые запросы, но занимают место и немного замедляют запись. Для MVP точно нужны минимальные индексы:

- уникальный индекс на `User.email`, чтобы email не повторялся
- индекс на `Recipe.ownerId`, чтобы быстро получать рецепты конкретного пользователя
- возможно составной индекс `Recipe.ownerId + Recipe.createdAt` или `Recipe.ownerId + Recipe.updatedAt`, если список рецептов будет сортироваться по дате

Индексы под будущий полнотекстовый поиск по рецептам, ингредиентам и описаниям лучше не закладывать заранее. Когда появится поиск, можно будет выбрать подход: PostgreSQL full-text search, trigram indexes или отдельный поисковый движок.

Рекомендация для MVP: оставить только минимальные индексы `email`, `ownerId` и, если список рецептов сортируется по дате, `ownerId + createdAt`.

## Безопасность

### 45. Cookie сессии: httpOnly, secure в production, sameSite `lax` подходит?

Ответ:да

### 46. Нужна ли CSRF-защита отдельно, или полагаемся на sameSite + Server Actions?

Ответ: Не нужна пока базовая защита

Пояснение от агента:

CSRF — это атака, при которой пользователь уже авторизован на нашем сайте, а вредоносный сайт пытается заставить его браузер выполнить действие от его имени. Например, отправить форму удаления рецепта, потому что браузер автоматически прикладывает cookie сессии.

Для MVP с Next.js Server Actions базовый безопасный вариант:

- хранить session cookie как `httpOnly`
- использовать `sameSite: "lax"`
- включать `secure: true` в production
- проверять права пользователя на каждое действие на сервере

Отдельный CSRF-token на MVP можно не вводить, если все мутации идут через Server Actions и нет публичного cookie-based API для внешних клиентов. Если позже появятся API routes для внешних клиентов или сложные интеграции, вопрос CSRF стоит пересмотреть.
